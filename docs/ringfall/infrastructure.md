# RINGFALL infrastructure handoff (TKT-44, #134, #135, #136)

This branch is preparation only. It has not queried or changed a Cloudflare account.

## Ownership

| Item | Owner / source of truth |
| --- | --- |
| D1 database `ringfall` lifecycle | OpenTofu `infra/ringfall/main.tf`; names in `config.json` |
| D1 schema | `migrations/0001_init.sql`, applied explicitly with Wrangler |
| Game Worker and island Worker code, versions, deployments, assets, bindings | Wrangler and the existing Vite/Workers Builds path |
| IslandDO SQLite namespace migration | `islands/wrangler.jsonc` v1; applied by deploying the island Worker |

OpenTofu does not declare Workers or bindings. Wrangler does not create the D1 database. This avoids competing writers for a Worker version, including its complete binding set and Vite assets. The [Cloudflare IaC guide](https://developers.cloudflare.com/workers/platform/infrastructure-as-code/) says its Terraform upload example does not bundle Workers; it specifically recommends Wrangler for bundling and permits managing only part of the Worker lifecycle in Terraform. It also notes that a DO migration/binding may require a staged deployment. D1 SQL migrations are [managed by Wrangler](https://developers.cloudflare.com/d1/reference/migrations/) and are not hidden in a Tofu `local-exec` provisioner.

`infra/ringfall/config.json` is the SSOT for infrastructure names and binding names. The generator checks the island Worker name/migration and Worker code's fixed binding names. The checked-in root `wrangler.jsonc` stays unbound, so merging this preparation cannot point a production Worker at a nonexistent database. `scripts/ringfall-wrangler-config.mjs` produces a private `wrangler.migration.jsonc` or `wrangler.connected.jsonc` in the repository root from a **real** D1 UUID. These files are ignored by Git. The generator fails if the root config has acquired bindings; reconcile any new configuration before using it. Do not commit an account ID, database ID, token, `.tfvars`, or state.

## Preconditions before any real action

The account owner must identify the correct account ID, existing D1 database (if any), existing Worker names/routes, Workers Builds projects and deploy commands, API token scope, current plan, quota/usage, alerts, backups, state backend, and any Cloudflare dashboard changes. None was confirmed for this PR. Check the current `main` and all open PRs again. Verify whether the production root Worker is deployed by Builds on every push; if so, retain the unbound checked-in config until the staged release is ready. Configure protected, shared OpenTofu state before `plan` or `apply`; a local state file is unsuitable for shared production management. Confirm whether a D1 database already exists: **import it after confirming account and ID**, instead of creating a duplicate. Inspect the plan for replacement/deletion and stop if either appears. `prevent_destroy` is a safeguard, not a substitute for reviewing the plan. No commands below have been run against a real account.

## Staged release (manual, after separate production approval)

1. Pin and initialize the Cloudflare provider in the chosen protected state backend. Supply the actual account ID via `TF_VAR_cloudflare_account_id`, and the API token through the provider's `CLOUDFLARE_API_TOKEN` environment variable. Run `tofu fmt -check`, `tofu validate`, and review `tofu plan` from `infra/ringfall`. For an existing database, verify its name and account, then use `tofu import cloudflare_d1_database.ringfall <account-id>/<database-id>` **only after confirming the provider's current import syntax**. Review a second plan for no destructive changes. Apply only with separate authorization. Record the actual output `tofu output -raw ringfall_database_id` privately.
2. Generate a migration-only config in the root: `node scripts/ringfall-wrangler-config.mjs migration "$D1_ID" wrangler.migration.jsonc`. Check the generated name and ID against the account. Run `npx wrangler d1 migrations list ringfall --remote --config wrangler.migration.jsonc`, inspect `migrations/0001_init.sql` and existing tables, take a backup as required by the operator, then explicitly run `npx wrangler d1 migrations apply ringfall --remote --config wrangler.migration.jsonc`. Verify `players`, `island_summaries`, and `raids` exist. Stop on mismatch. Do not deploy the game Worker yet.
3. Inspect existing `ringfall-islands` Worker and its migrations. Deploy `npx wrangler deploy --config islands/wrangler.jsonc` only after verifying account, route, compatibility and existing DO state. This creates the SQLite `IslandDO` namespace through the checked-in v1 migration if it does not already exist. Verify the deployed Worker and namespace before proceeding. Decide whether a separate Workers Builds project should own future island Worker deployments; this PR does not change Builds settings.
4. Generate `wrangler.connected.jsonc` with `node scripts/ringfall-wrangler-config.mjs connected "$D1_ID" wrangler.connected.jsonc`. Review all fields, especially the `DB` and cross-script `ISLAND` bindings, then use it in a separately approved deployment path. The existing Vite plugin reads root `wrangler.jsonc` during `npm run build`, so test an isolated checkout with the generated config installed as root `wrangler.jsonc` before changing production Builds. Rebuild and deploy the game Worker only after verifying Vite assets are included. Do not blindly push a bound root config: Builds may deploy on push, and their actual configuration remains unverified.
5. Verify the real API: a completed raid must make `POST /api/island` succeed instead of 202/503; query `SELECT COUNT(*) FROM island_summaries` against the intended remote D1. `GET /api/islands/<code>` should return 200. Perform the separate-storage two-browser expedition and retake sequence in [#136](https://github.com/tktcorporation/game-sandbox-tsx/issues/136). The existing screenshot gate suppresses network requests and cannot establish this result.

If a stage fails, stop before adding the next dependency. Revert the game Worker deployment to its previous known version/config to remove new bindings if needed; keep the D1 and island Worker intact pending diagnosis. Use the recorded D1 backup/restore procedure for schema or data incidents. Do not remove D1 or DO state as a rollback shortcut.

No free-operation guarantee is possible without the account's plan and usage. Check current [D1](https://developers.cloudflare.com/d1/platform/pricing/), [Durable Objects](https://developers.cloudflare.com/durable-objects/platform/pricing/), [Workers](https://developers.cloudflare.com/workers/platform/pricing/) and [Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/limits-and-pricing/) billing and limits, abuse controls for anonymous island claims, spending alerts, access permissions, backup/restore, and operational ownership before production use.
