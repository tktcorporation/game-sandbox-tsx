These are the [November 11, 2026 Node security releases](https://nodejs.org/en/blog/vulnerability/november-2026-security-releases), which meet `CLAUDE.md`'s known-vulnerability exception to its 14-day rule. The local build passed on Node 24.22.3. Verify the actual Node version in Workers Builds; this source change does not update its saved runtime settings.

## Future Mac DevContainer setup

`.devcontainer/devcontainer.json` is a **new, unstarted definition** for this repository, not a claim that a RINGFALL DevContainer already exists. It uses the [official Node 24.22.3 Bookworm image](https://hub.docker.com/_/node/tags) (published for Linux arm64 and amd64), the non-root `node` user, a bind mount of this repository only, dropped Linux capabilities and `no-new-privileges`. It declares no Docker socket, host home, SSH, secret, or other-repository mounts; no shared credential volume; no features, startup installer, build or deployment hook. `npm ci` later installs the lock-pinned `cf` CLI and Vite dependencies into the repository's `node_modules`; the DevContainer definition does not run it automatically. The Node patch is within the security exception described above.

The toolchain gate is `node scripts/ringfall-devcontainer-preflight.mjs`. It checks Linux arm64/amd64, non-root execution and exact versions of Node 24.22.3, OpenTofu 1.13.2, SOPS 3.13.2, and age 1.3.2. It runs only local `version`/`--version` commands, with a PATH-only child environment. It does not inspect credentials, state, or Cloudflare. Until the three tools are installed, failure is expected. It is a toolchain check, **not** authorization to run OpenTofu state commands; `npm run tofu:preview -- init/plan/apply` still refuses them.

Use the official [OpenTofu v1.13.2 release](https://github.com/opentofu/opentofu/releases/tag/v1.13.2) and [standalone verification instructions](https://opentofu.org/docs/intro/install/standalone/), [SOPS v3.13.2 release and signed checksums](https://github.com/getsops/sops/releases/tag/v3.13.2), and [age v1.3.2 release](https://github.com/FiloSottile/age/releases/tag/v1.3.2). Select the **Linux arm64** artifacts inside an Apple Silicon container, or Linux amd64 artifacts on an Intel Mac. Confirm the selected release artifact and its verified checksum/signature before placing `tofu`, `sops`, and `age` in the container user's `~/.local/bin` and adding that directory to PATH; do not run unreviewed installer scripts or disable signature verification. The versions are fixed for this preparation: OpenTofu 1.13.2 was released October 21 and contains security fixes; SOPS 3.13.2 and age 1.3.2 also predate the 14-day dependency window. The separate earlier local `tofu fmt` used 1.13.9, but that version was released November 5 and is not adopted here under the 14-day rule. Review any version change with the same rule and repeat the gate.

Before a later first start on the Mac: confirm that the existing Docker-compatible runtime (OrbStack on this Mac) is running and that the execution environment has authorized access to its socket. Docker Desktop installation is unnecessary. Check available disk and network access to Docker Hub and the official tool release hosts, then open this repository in the Dev Container. Pulling the image downloads approximately 382 MB compressed on arm64, plus extracted layers; `npm ci` downloads packages and writes `node_modules` in the bind-mounted repository; tool downloads and a build add disk usage. The container binds only this checkout and has no named volume, so deleting it removes its container-local `~/.local/bin` tools; the checkout and `node_modules` remain on the Mac. Docker pull, npm and tool downloads need outbound network; a later `cf build` can also use network. No Cloudflare request is required to start the container or run the toolchain gate. No port is published by this definition. Review any further port forwarding before local `cf dev`.

After opening, install the three verified binaries as the non-root user, run `npm ci`, then run the gate and the existing safe checks (`npm run test:tofu-preview`, `npm run test:cf-config`, `npm run build`). Do not provide the container with a recovery key, token, state, or 1Password mount as part of this setup. Preparation of a dedicated short-lived credential, RINGFALL-only SOPS/age key and 1Password recovery path is already approved; the formal connection and storage destination needed to carry out that approved work, and the authoritative Preview state, still need to be confirmed. The Mac's 1Password MCP is currently unregistered. Docker socket access was denied from dot's read-only execution environment with the Mac selected, despite matching socket ownership; having a CLI installed does not establish permission to connect. This source change resolves neither condition. No actual container build, start or binary installation has been tested by this PR.

## Build and release entrypoints

The npm scripts are the repository's command contract. `npm run builds:build` runs the TypeScript check and `cf build --mode production`. It produces `.cloudflare/output/v0/` with mode `production`, including the Vite assets. `npm run builds:deploy` runs `cf deploy --prebuilt --mode production`: **it uploads and changes production traffic**. `npm run builds:version` runs `cf workers versions create --prebuilt --mode production`: **it uploads a version without switching production traffic**. Both upload commands require a matching Build Output from `builds:build` in the same job or restored artifact. `npm run deploy` combines the build and production deploy. `npm run dev` and `npm run preview:local` both run `cf dev` locally; neither is a Cloudflare Preview deployment. The old `vite preview` script is removed.

`npm run builds:preview` runs the type check and `cf previews deploy --mode production` for a PR branch. This is a **remote Preview deployment**: cf builds again with `isPreview=true`, then uploads a branch-isolated Preview. It must only run after the dedicated Preview D1 and its SQL schema are ready, and after separate approval for Preview resource creation. It is not a safe dry-run command, and this PR has not invoked it. Do not pass production Build Output to Preview with `--prebuilt`; production output has `isPreview=false` and would carry production bindings. The [cf Preview build rule and model](https://developers.cloudflare.com/cf/projects/) are the references.

The version-only path is a non-production **upload**, not a working Preview for this Durable Object Worker: its Version URL is unsupported. It remains a temporary fallback for older PRs such as #23. On the current PR, that upload stopped after the asset stage because `ISLAND` points at `IslandDO` before its namespace has been provisioned. A first deployment must reconcile the namespace; repeated version-only uploads will not do so.

The agreed target is PR branches → Worker Previews and main → production; no new production branch. The saved Builds branch filters and commands still need read-back before switching. The external main **build command** should be `npm run builds:build` and its **deploy command** `npm run builds:deploy`. A PR Preview trigger should run `npm run builds:preview` with the dedicated D1 ID in that trigger's environment. This command builds its own Preview output; the main build command must not feed it production output. The current shared Version command conditionally uses `npm run builds:version` when present and legacy Wrangler otherwise for old PRs. Retire that fallback only after old PR paths no longer need it, Preview D1 and namespace initialization are reviewed, PR branch filters and command are confirmed, and Preview QA succeeds. First inspect the actual settings and confirm which branch each trigger builds. Do not change an external command until that trigger's branch contains the scripts. Then align the commands once and read saved values back. The outer Builds command is selected before `cloudflare.config.ts` is evaluated, so code cannot repair a saved Wrangler command automatically. Do not add a push-time self-updater. Workers Builds must use a supported Node version; `.node-version` requests 24.22.3, and `package.json` records the engine range. Check the effective version in build logs.

## Ownership

| Item | Owner / source of truth |
| --- | --- |
| Production D1 `ringfall` lifecycle | OpenTofu root `infra/ringfall`; production address `cloudflare_d1_database.ringfall` is unchanged. |
| Shared Preview D1 `ringfall-preview` lifecycle | Independent OpenTofu root `infra/ringfall-preview`; its only resource is `cloudflare_d1_database.ringfall_preview`. Both roots read names from `infra/ringfall/config.json`. Neither root includes the other's resource or a module reference. |
| D1 schema | `migrations/0001_init.sql`; explicit `cf d1 migrations` operation |
| Game Worker, `IslandDO` export and self binding, code, assets, versions and deployment | `cloudflare.config.ts`, `worker/index.ts`, Vite, and `cf` |

The root Worker exports `IslandDO` and binds to that class in the same Worker. `cf` declares its SQLite lifecycle with `exports.durableObject({ storage: "sqlite" })`, replacing the separate island Worker and its Wrangler v1 migration **in source only**. This does not authorize deletion or transfer of any real namespace or Worker. If an existing `ringfall-islands` Worker or DO namespace is found, stop and design its migration using Cloudflare's [transfer procedure](https://developers.cloudflare.com/cf/projects/cloudflare-config/#transfer-a-class-between-workers) before deploying. Do not infer that absence from this repository means absence in the account.

For production, `cloudflare.config.ts` includes `DB` only when `RINGFALL_D1_DATABASE_ID` is a UUID. The production database name comes from the same JSON file OpenTofu reads. For Preview, `isPreview=true` **requires** `RINGFALL_PREVIEW_D1_DATABASE_ID`, rejects the production ID, and binds by ID only; it never falls back to production or supplies a D1 name that cf could use to provision one. No account or database ID is committed. The same `ISLAND` self binding and SQLite `IslandDO` export are declared for both builds. Cloudflare isolates the Preview DO namespace, but D1 IDs are explicit: if all PR branches receive the same Preview D1 ID, they share that Preview database. Supply separately managed IDs per branch if PR-to-PR D1 isolation is required. The config evaluation test checks binding shape but cannot prove the actual Preview namespace created by Cloudflare; inspect it after an approved first Preview deployment. `env.ISLAND` remains the runtime path used by the game. Vite owns the static assets output and preserves the three HTML entrypoints in `vite.config.ts`; the cf config owns asset runtime behavior and the `ASSETS` binding. `cf build` and `cf deploy --dry-run` validate **production** Build Output without uploading. Production traffic and saved Workers Builds settings are not changed by this PR.

The old `wrangler.jsonc`, `islands/` Worker entry/config, and generated Wrangler config script were removed because the project is unreleased and the approved target is one cf Worker. The existing `worker/island.ts` rules and `worker/island-do.ts` implementation remain. The D1 migration remains the SQL source of truth. Cf expects the D1 **ID** in migration commands, and migrations are remote by default, so operators must take care with the commands below. See the [cf migration guide](https://developers.cloudflare.com/cf/wrangler/migrate/#d1-migrations).

### OpenTofu state gate before a later authorized run

The production and Preview directories are **independent roots**. Neither has a backend block. OpenTofu would default to a new local state file; `tofu init -backend=false` used for earlier syntax preparation is not evidence of authoritative state. `npm run tofu:preview -- fmt` always selects the Preview root and runs only `tofu fmt -check`, with inherited Cloudflare tokens removed. `npm run tofu:preview -- preflight` checks the shape of `TF_VAR_cloudflare_account_id` without printing it or contacting Cloudflare. The entrypoint refuses `init`, `validate`, `plan`, `import`, `apply`, `state`, extra arguments and caller-supplied root overrides. It is a code-preparation gate, not approval or proof of state ownership. The account inventory on 2026-11-16 found no resource identifiable as RINGFALL D1/DO and the production Worker had only `ASSETS`, but it cannot prove that state or differently named resources do not exist.

1. Find the authoritative state owner and backend **for each root** from deployment records, CI configuration and the account owner. Confirm account, state identity, access policy, encryption, locking, recovery backup and single-writer procedure. The existing CALENBOT private encrypted-state/SOPS/age approach is a design candidate, not a configured RINGFALL backend: do not copy its keys, token or state. If either root's state cannot be established, **stop**. Do not invent a backend or let a fresh local state become authoritative.
2. With separate authorization, protect and inspect both existing states and compare tracked addresses/IDs with read-only Cloudflare inventory. Preserve production `cloudflare_d1_database.ringfall`. **Before any production-root plan/apply with this PR**, confirm its old state does not track `cloudflare_d1_database.ringfall_preview`: removing its declaration from the old root could otherwise plan destruction. If the Preview D1 is tracked there or at any other address, stop for a separately reviewed, backed-up state split/move. Do not apply either root, import into a second state, or remove the old address until one owner is established. Cross-root migration is a state operation and is not performed here.
3. If a D1 exists but is untracked, stop for a separately reviewed import into the Preview root after verifying account and real ID. If neither state nor account has it, only then review a create plan. `prevent_destroy` blocks some deletion paths but does **not** prevent duplicate creation or prove state ownership. Never decide ownership from a name match alone.
4. Establish the approved RINGFALL-specific backend, authentication injection and protected state/plan handling in a later change. `.gitignore` excludes plaintext state and backups, tfvars including JSON, provider working directories and conventional saved plans in both roots; keep any future plan under `plans/` or name it `*.tfplan`/`*.plan`, and protect it outside Git as sensitive material. Ignore rules are a safeguard, not encryption or authorization. A format check or successful preflight must not be used as permission to run `init`. ### Preview encryption template and recovery boundary

`infra/ringfall-preview/encryption.tf` is a **Preview-only, secretless template**. It defines PBKDF2/AES-GCM for both state and saved plans, with `enforced = true` and a sensitive `preview_state_passphrase` variable with no default. The passphrase is absent from this repository. OpenTofu's [state and plan encryption guidance](https://opentofu.org/docs/language/state/encryption/) confirms that enforcement prevents an unencrypted fallback, and that the correct key is required to recover state. It does not protect against lost or rolled-back state. The production root is unchanged. The Preview root still has **no selected backend, authoritative state, key custody, or Cloudflare credential**; this template is not ready for `init`, `plan`, or `apply`. The current npm entrypoint continues to refuse those commands.

Before enabling any state command in a later reviewed change, the owner must identify any existing state and its encryption status, choose a RINGFALL Preview-specific protected store with a single-writer/locking policy, and confirm the Cloudflare account and least-privilege credential. An existing plaintext state needs a separately reviewed migration; do not add an `unencrypted` fallback here. Choose a dedicated high-entropy passphrase, record its version and recovery custodian, and keep the encrypted state, saved plans, backups and key recovery material in separately protected locations. Test recovery on an isolated copy and check state lineage/serial before using a restored state. Do not copy CALENBOT's state, age key or token, and do not give a decryption key to CI.

The later approved runner should obtain the Preview-only passphrase and Cloudflare credential from the designated external secret store, hold them in memory, and pass only `TF_VAR_preview_state_passphrase`, `TF_VAR_cloudflare_account_id` and the scoped Cloudflare credential to its **tofu child process**. It must fix `infra/ringfall-preview` as the root, avoid shell interpolation and logging of values, and never write a `.env`, tfvars, plaintext state or plan into Git. Its exact backend and authentication adapter remain to be selected and reviewed. This design does not authorize creating a key, token, backend or state in this PR.

`scripts/ringfall-preview-auth-contract.mjs` is a **stub-only contract**, not an executable SOPS or Tofu runner. It expects a future SOPS JSON decryption adapter to return exactly three fields: `cloudflare_account_id`, `cloudflare_api_token`, and `preview_state_passphrase`. It parses JSON directly, rejects extra/missing fields, and maps only those fields to a child environment. It requires a single-writer adapter before decryption, fixes the Preview root, and sanitizes child/decryption errors. No shell `eval`, SOPS command, real spawn, auth store, or state command is wired. The current `tofu:preview` command still permits only fmt/preflight. A Worker Editor credential can deploy production; its mere possession is not proof of Preview-only scope. Confirm the actual account, permission and exposure before using any credential.

For a future private-repo encrypted-state workflow, designate one Preview state artifact, one writer and one recovery owner. Record the exact code commit, provider lockfile, state lineage/serial and encrypted artifact hash for each approved change; reject stale serials and non-fast-forward pushes. Git history is **not** a distributed lock. Use a real single-writer gate now and a locking backend before multiple runners. Keep a separately protected recovery copy and test decryption and restoration on an isolated copy. The owner's 1Password recovery key and SOPS/age recipient would be dedicated to RINGFALL; do not copy another project's key or deliver the decryption key to CI. The existing `.gitignore` continues to exclude all `*.tfstate*`, even ciphertext. **No exception is added now** because no state artifact, ciphertext verifier, custody process or approved backend exists; an exception without those checks could permit plaintext to be committed. Git tracking of verified encrypted state needs a separate reviewed change.
