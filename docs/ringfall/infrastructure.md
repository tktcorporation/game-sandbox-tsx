# RINGFALL infrastructure (#124, #134–#136, TKT-44)

This PR prepares a **single Worker**. This branch has not created a Preview, D1, or Durable Object namespace, changed Cloudflare settings, or deployed production traffic. A Cloudflare Builds run for this PR uploaded nine assets, then its version-only upload stopped because `IslandDO` had not been provisioned. The [Cloudflare CLI `cf`](https://developers.cloudflare.com/cf/) is the open beta project CLI, separate from the Cloudflare OpenTofu provider. Its configuration and Build Output may change during beta.

This repository pins `cf` 1.0.0-beta.24, the Cloudflare Vite plugin 2.0.0-beta.v.8, and Vite 7.3.7. All were at least 14 days old on 2026-11-14, as required by `CLAUDE.md`. The local build used Node 24.22.0; verify a supported Node version in Workers Builds before changing its commands.

## Build and release entrypoints

The npm scripts are the repository's command contract. `npm run builds:build` runs the TypeScript check and `cf build --mode production`. It produces `.cloudflare/output/v0/` with mode `production`, including the Vite assets. `npm run builds:deploy` runs `cf deploy --prebuilt --mode production`: **it uploads and changes production traffic**. `npm run builds:version` runs `cf workers versions create --prebuilt --mode production`: **it uploads a version without switching production traffic**. Both upload commands require a matching Build Output from `builds:build` in the same job or restored artifact. `npm run deploy` combines the build and production deploy. `npm run dev` and `npm run preview:local` both run `cf dev` locally; neither is a Cloudflare Preview deployment. The old `vite preview` script is removed.

`npm run builds:preview` runs the type check and `cf previews deploy --mode production` for a PR branch. This is a **remote Preview deployment**: cf builds again with `isPreview=true`, then uploads a branch-isolated Preview. It must only run after the dedicated Preview D1 and its SQL schema are ready, and after separate approval for Preview resource creation. It is not a safe dry-run command, and this PR has not invoked it. Do not pass production Build Output to Preview with `--prebuilt`; production output has `isPreview=false` and would carry production bindings. The [cf Preview build rule and model](https://developers.cloudflare.com/cf/projects/) are the references.

The version-only path is a non-production **upload**, not a working Preview for this Durable Object Worker: its Version URL is unsupported. It remains a temporary fallback for older PRs such as #23. On the current PR, that upload stopped after the asset stage because `ISLAND` points at `IslandDO` before its namespace has been provisioned. A first deployment must reconcile the namespace; repeated version-only uploads will not do so.

The agreed target is PR branches → Worker Previews and main → production; no new production branch. The saved Builds branch filters and commands still need read-back before switching. The external main **build command** should be `npm run builds:build` and its **deploy command** `npm run builds:deploy`. A PR Preview trigger should run `npm run builds:preview` with the dedicated D1 ID in that trigger's environment. This command builds its own Preview output; the main build command must not feed it production output. The current shared Version command conditionally uses `npm run builds:version` when present and legacy Wrangler otherwise for old PRs. Retire that fallback only after old PR paths no longer need it, Preview D1 and namespace initialization are reviewed, PR branch filters and command are confirmed, and Preview QA succeeds. First inspect the actual settings and confirm which branch each trigger builds. Do not change an external command until that trigger's branch contains the scripts. Then align commands once and read saved values back. The outer Builds command is selected before `cloudflare.config.ts` is evaluated, so code cannot repair a saved Wrangler command automatically. Do not add a push-time self-updater. Workers Builds must use a supported Node version; `.node-version` requests 24.22.0, and `package.json` records the cf-supported engine range. Check the effective version in build logs.

## Ownership

| Item | Owner / source of truth |
| --- | --- |
| Production D1 `ringfall` lifecycle and future dedicated Preview D1 lifecycle | OpenTofu; current production declaration is `infra/ringfall/main.tf`, with its name in `infra/ringfall/config.json`. Add a separately reviewed Preview D1 declaration before its first real use. |
| D1 schema | `migrations/0001_init.sql`; explicit `cf d1 migrations` operation |
| Game Worker, `IslandDO` export and self binding, code, assets, versions and deployment | `cloudflare.config.ts`, `worker/index.ts`, Vite, and `cf` |

The root Worker exports `IslandDO` and binds to that class in the same Worker. `cf` declares its SQLite lifecycle with `exports.durableObject({ storage: "sqlite" })`, replacing the separate island Worker and its Wrangler v1 migration **in source only**. This does not authorize deletion or transfer of any real namespace or Worker. If an existing `ringfall-islands` Worker or DO namespace is found, stop and design its migration using Cloudflare's [transfer procedure](https://developers.cloudflare.com/cf/projects/cloudflare-config/#transfer-a-class-between-workers) before deploying. Do not infer that absence from this repository means absence in the account.

For production, `cloudflare.config.ts` includes `DB` only when `RINGFALL_D1_DATABASE_ID` is a UUID. The production database name comes from the same JSON file OpenTofu reads. For Preview, `isPreview=true` **requires** `RINGFALL_PREVIEW_D1_DATABASE_ID`, rejects the production ID, and binds by ID only; it never falls back to production or supplies a D1 name that cf could use to provision one. No account or database ID is committed. The same `ISLAND` self binding and SQLite `IslandDO` export are declared for both builds. The config evaluation test checks this shape but cannot prove the actual Preview namespace created by Cloudflare; inspect it after an approved first Preview deployment. `env.ISLAND` remains the runtime path used by the game. Vite owns the static assets output and preserves the three HTML entrypoints in `vite.config.ts`; the cf config owns asset runtime behavior and the `ASSETS` binding. `cf build` and `cf deploy --dry-run` validate **production** Build Output without uploading. Production traffic and saved Workers Builds settings are not changed by this PR.

The old `wrangler.jsonc`, `islands/` Worker entry/config, and generated Wrangler config script were removed because the project is unreleased and the approved target is one cf Worker. The existing `worker/island.ts` rules and `worker/island-do.ts` implementation remain. The D1 migration remains the SQL source of truth. Cf expects the D1 **ID** in migration commands, and migrations are remote by default, so operators must take care with the commands below. See the [cf migration guide](https://developers.cloudflare.com/cf/wrangler/migrate/#d1-migrations).

## Preview initialization after separate approval

1. Add a dedicated Preview D1 to OpenTofu with a distinct name and protected state. Inventory and import any existing intended Preview D1 before planning creation. Review the plan, then apply only with separate authorization. Keep its ID in the PR Preview Builds environment as `RINGFALL_PREVIEW_D1_DATABASE_ID`; set `RINGFALL_D1_DATABASE_ID` there too if available so the inequality guard can verify it. Do not put either ID in source.
2. Review and explicitly apply `migrations/0001_init.sql` to the Preview D1. Verify `players`, `island_summaries`, and `raids` before exposing a Preview. Schema operations are separate from OpenTofu and cf deploy.
3. Inspect the actual Preview branch filters, command, routes, cost and namespace model. Only after the target branch contains `builds:preview`, switch that PR trigger to `npm run builds:preview`. Its `cf previews deploy` builds with `isPreview=true`; a normal `npm run builds:build` is a production-mode build and is not its input. The first approved Preview deploy may provision its isolated `IslandDO` namespace. Read the resulting bindings and namespace back and verify they do not reference production D1 or DO state. The local config test does not establish that remote separation.
4. Run #136 real two-browser QA against the Preview. A newly claimed island cannot receive expeditions for **two days**. The screenshot gate suppresses server requests and cannot establish real connectivity.

Record every Preview and its D1/DO inventory and retention owner. On PR close or merge, review data retention and any linked routes, then remove the Preview and dedicated resources through a separately approved cleanup. Do not automate D1 or DO deletion as part of this PR; Cloudflare's actual Preview lifetime and billing behavior still need account-level verification.

## Staged release after separate approval

1. **DB** — In `infra/ringfall`, initialize a protected backend and verify the Cloudflare provider and account. If a `ringfall` D1 already exists, confirm its owner and import it with the provider's current import syntax. Otherwise review a create plan. Inspect the plan for replacement or deletion; `prevent_destroy` is only a safeguard. Apply only with explicit production authorization and record `tofu output -raw ringfall_database_id` privately.
2. **SQL** — Inspect the intended D1 and `migrations/0001_init.sql`; arrange a backup. From repo root run `cf d1 migrations list "$RINGFALL_D1_DATABASE_ID" --dir migrations` and, after review, explicitly run `cf d1 migrations apply "$RINGFALL_D1_DATABASE_ID" --dir migrations`. These target remote D1 by default; `--local` is only for local rehearsal. Verify the `players`, `island_summaries`, and `raids` tables before enabling `DB` on a deployment. A missing schema makes API writes fail with 503.
3. **Worker** — Check whether the old `ringfall-islands` Worker or namespace was actually deployed. If yes, stop for a separately reviewed data transfer plan. If no, verify `npm run builds:build` and a local `cf deploy --dry-run --prebuilt --mode production` with the actual D1 ID in a secure environment, inspect assets, routes and binding output, then deploy the single Worker only with separate authorization. Do not use a name-only D1 binding; cf may provision a resource for it. Update Workers Builds only after confirming its current configuration and deployment trigger and that its target branch contains the scripts.
4. **Real QA** — Complete a raid and verify `POST /api/island` succeeds instead of 202 (`no-database`) or 503 (`db-error`); query the actual D1 summary. Verify an island code and `GET /api/islands/<code>` returns 200. Use two browsers with separate storage to perform [#136](https://github.com/tktcorporation/game-sandbox-tsx/issues/136), including expedition, capture, retake and income. A newly claimed island cannot receive expeditions for **two days**. The screenshot gate suppresses server requests and is not evidence of real connectivity.

If any stage fails, stop before the next. Return the game Worker to a known good version/config if a deployment fails; preserve D1 and DO state while diagnosing. For a schema or data incident, use the reviewed backup and restore plan. Never delete D1, a Worker or a DO namespace as an automatic rollback.
