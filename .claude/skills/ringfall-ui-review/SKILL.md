# RINGFALL の UI 点検

ゲームの仕組みは PR ごとに変わるのに、画面は前の仕組みのまま残りやすい。数字やランクが、今の目的と関係のないものを測ったまま表示され続ける。選択肢は、プレイヤーが選ぶ理由が書かれないまま残る。点検では、1 画面ずつの見た目ではなく、プレイヤーが 1 日を通して見る画面の並びを、今の仕組みと突き合わせる。

## 1. 今の仕組みを掴む

点検の前に次を読み、プレイヤーが今何を目指していて、1 日に何を決めるのかを、自分の言葉で 3 行に書く。この 3 行が、以降の判定の基準になる。

- `CLAUDE.md` の RINGFALL の節
- `docs/ringfall/` の設計資料（brief、島・前線・陣取り戦の資料）

## 2. 画面を撮る

`npm run shots:ringfall` を回す（約 18 分。重い処理と同時に 2 つまで）。各スクリーンショットがどの状態で撮られたかの正本は `scripts/ringfall-shots.mjs` にある。番号から場面を推測せず、スクリプトを読む。

撮られていない画面や状態があれば、点検の前にそのスクリプトへ撮影を足す。点検した画面は、次の点検でも撮られるようにする。

## 3. 旅の順に見る

スクリーンショットを、デスクトップ版とスマホ版（`m` で始まるもの）の両方で、次の順に Read で見る。

1. **開始画面**：タイトル
2. **準備**：野営地と各設備のパネル（倉庫・装備、依頼板、地図の机、工房、工場、商人、隠れ家）
3. **戦闘中**：HUD、目的のカード、方位、地図、精算前の脱出
4. **リザルト**：精算画面のすべてのカード
5. **リザルト後**：次の日の野営地、終わりの画面

## 4. 各画面で問うこと

画面ごとに次の 5 つを問う。値の意味は、画面の文言からではなく、その値を計算するコード（`src/ringfall/meta/`、`src/ringfall/sim/`）を読んで確かめる。

- **測っているもの**：数字・ランク・印のそれぞれが何から計算されているか。それは手順 1 の目標と結び付いているか。前の仕組みの名残ではないか
- **選択の理由**：プレイヤーに選ばせているものは、プレイヤーが決めるべきことか。何を得て何を払う選択かが、選ぶ場所に書かれているか
- **手間**：よくする操作に何手かかるか。前回と同じ選択を毎回やり直させていないか。選ぶ瞬間に要る情報（武器の性能、所持数、行き先）が、その画面にあるか。取り消せない操作の前に確認があるか
- **一貫性**：同じものを画面ごとに別の名前・色で呼んでいないか。逆に、別のものを同じ言葉で呼んでいないか。凡例と実際の色・並びが一致しているか
- **次の一手**：その画面を閉じたとき、プレイヤーは次に何をすればいいか分かるか。必要な情報が、別の画面に行かないと見えない状態になっていないか

スマホ版では、画面に収まらずにスクロールしないと見えない重要な情報と、指で押しにくい操作を、別に確かめる。

## 5. 報告する

指摘は画面の順にまとめ、各指摘に次を書く。

- **重さ**：高・中・低
- **見えているもの**：スクリーンショットのファイル名
- **原因**：値や挙動を決めているコードの `ファイル:行`
- **直し方**：具体的な案
- **種類**：「表示だけ」（文言・配置・色・既定値の表示）か「設計判断が要る」（ルール・報酬・機能の有無を変える）か

最後に、直す順の上位 10 件を並べる。「設計判断が要る」ものは実装する前にユーザーに方針を確かめ、「表示だけ」のものから直してよい。
