# ゲームを判断のループとして組み立てる

面白さは「ジャンルの特徴をいくつ揃えたか」では決まらない。図鑑・進化・通貨・タイマーを揃えても、プレイヤーが下す判断が無ければ眺めるだけの画面になる。本スキルは、ゲームを**判断のループ**として定義し、そのループが成立しているかを検査し、数値をシミュレーションで決め、遊んで確かめ、分かったことを記録する手順を固定する。

## 位置づけ

- `ui-craft`：見た目の意図（型・余白・色・質感）を決める
- **本スキル**：何を判断させ、その判断に必要な情報を何で見せ、結果をどう返すかを決める。UI の「何を置くか」は本スキル、「どう見せるか」は `ui-craft`
- `.claude/rules/` の文章規範：本スキルが書く教訓と目標曲線の文体

## 前提となる考え方

プレイヤーが 1 周で体験することを、次の 5 要素に分解する。

| 要素             | 問い                                                   |
| ---------------- | ------------------------------------------------------ |
| 情報             | 判断の前に、何が画面に見えているか                     |
| 判断             | 何と何の間で迷うか。迷わないなら判断ではない           |
| 動詞             | 判断を実行する操作は何か                               |
| フィードバック   | 結果が、判断の良し悪しとして返ってくるか               |
| 積み上がるもの   | 次の周に持ち越されて、次の判断を変えるものは何か       |

5 つのどれかが欠けると、その周は「作業」か「観賞」になる。診断も設計も、この 5 要素が全部あるかを見ることから始める。

## サイクル

1 サイクルは 1 つの判断を対象にし、1 つのコミットにまとまる粒度にする。ゲーム全体を一度に直さない。

### Step 0：診断する

対象のゲームで、プレイヤーが実際にやる操作を列挙し、それぞれに 5 要素の表を埋める。埋まらない列があれば、それが今回の対象になる。複数あるときは、プレイ時間の最も長い場面（戦闘・配置・生産）を優先する。

見つけやすい兆候は `references/anti-patterns.md` にある。診断の結論は「どの操作に、どの要素が欠けているか」の 1 文にする。

### Step 1：コアループを 1 文で書く

対象の操作について、次の型で 1 文を書く。

> プレイヤーは【情報】を見て【判断】し、【動詞】する。結果は【フィードバック】で返り、【積み上がるもの】が次の周を変える。

書けない要素があれば、実装に進まず設計に戻る。この 1 文は、コミットメッセージと `references/lessons.md` の見出しに使う。

### Step 2：判断を検査する

書いた判断が本物かを、4 条件で検査する。1 つでも欠けると、プレイヤーは数回で「どれを選んでも同じ」と学習し、以後の選択肢を信用しなくなる。

| 条件   | 検査                                                                                   |
| ------ | -------------------------------------------------------------------------------------- |
| 差     | 選択肢ごとに結果が違う。同じ関数を呼ぶだけの複数ボタンは判断ではない                   |
| 見える | 判断に必要な情報が、判断の前に画面にある。説明文で補っているなら情報が無い             |
| 非自明 | 最適解を一目で計算できない。ゲーム自身が最適解を出すボタン（おまかせ）を持つなら要注意 |
| 帰結   | 結果が次の判断に影響する。勝っても負けても同じ画面に戻るなら帰結が無い                 |

「おまかせ」のような自動選択は、残すなら**素朴な基準**（数値の合計順など）にする。プレイヤーが考えれば自動選択に勝てる余地が、判断の価値になる。

### Step 3：ループを閉じる

ゲーム内の各システム（通貨・建物・タイマー・ステータス）について、「どの判断に効いているか」を表にする。

| システム | 効いている判断 | 効き方 |
| -------- | -------------- | ------ |

「効いている判断」が空欄のシステムは、切るか、判断へ接続する。飾りとして残さない。判断の基準は 3 つ。

- 通貨は 1 つから始める。2 つ目は、特定の緊張（今使うか貯めるか）を作りたい場面が具体的に言えるときだけ足す
- タイマーは、待つ間に判断が生まれるときだけ置く。単に操作を遅らせるタイマーは、ブラウザのゲームでは退屈にしかならない
- 本家のジャンルで面白さを支えている半分（対戦相手・リスク・失うもの）を省いたなら、それに依存するシステムも一緒に省く

### Step 4：数値はシミュレーションで決める

ロジックが純粋関数に分かれていれば、UI 無しで対戦・生産を回せる。基準となる状態（序盤・中盤・終盤）と条件（有利・中立・不利）の組み合わせごとに、結果の分布を表にする。

手順は 3 つ。

1. **目標曲線を先に書く**。「序盤パーティは wave 2〜3 で倒れる」「中盤で有利属性なら 6 割勝つ」のように、状態 × 条件ごとの狙いを `references/<game>-targets.md` に置く
2. **現状を測る**。`npx tsx scripts/sim/<game>-<場面>.ts` で分布を出し、目標曲線と並べる
3. **1 つずつ数値を動かして再測定する**。変えた数値と結果の差分を、目標曲線のファイルに追記する

分布の読み方には 2 つの目印がある。ある列が 100% か 0% に集中していれば、その条件では判断が結果に効いていない。条件（有利・中立・不利）を変えても分布が動かなければ、その条件はゲームに存在しない。

数値を「それらしく」置いたまま UI へ進まない。シミュレーションが無いゲームには、先にシミュレーションを書く。

### Step 5：UI は判断に必要な情報だけを見せる

判断の前に見えるべき情報（Step 1 の【情報】）を、アイコン・数値・配置で画面に出す。説明文を書きたくなったら、それは画面に無い情報の印なので、文章ではなく表示を足す。

見せる順序は、判断に近いものを判断の操作の近くに置く。通貨の総額のような「今の判断に関係ない数」は、見出しに常駐させない。

### Step 6：5 分遊ぶ

実装したら、対象の操作を 5 分遊び、次の 4 つに答える。

1. もう一度やりたいと思ったか
2. 負けた（失敗した）とき、理由が分かったか
3. 次に何を変えれば良くなるか、思いついたか
4. 待っている間、何を考えていたか（何も考えていなければ待ち時間は削る）

1 つでも No があれば、それが次サイクルの Step 0 になる。スクリーンショットを撮り、情報が判断の前に見えているかを画面で確かめる。

### Step 7：記録する

サイクルで分かったことを 2 か所に書く。

- `references/lessons.md`：ゲーム名を含まない一般化した教訓を 1 行と、その根拠を 1〜2 文
- `references/<game>-targets.md`：目標曲線と、変更前後のシミュレーション結果

記録の書き方は `.claude/rules/conclusion-only-output.md` に従う。過程ではなく、確定した結論と根拠だけを残す。

## スキルの育て方

このスキルは、サイクルを回すたびに強くなる前提で書いてある。育て方の規則は 4 つ。

1. **教訓は一般化して書く**。ゲーム名・種族名・具体の数値を含む記述は `<game>-targets.md` へ。`lessons.md` は別のゲームでそのまま使える文だけを置く
2. **同じ教訓が 2 回出たら本文へ昇格させる**。Step 2 の検査条件や Step 3 の基準に、1 行の項目として足す
3. **本文の検査項目が 3 サイクル連続で何も検出しなければ references へ降格させる**。本文は、実際に問題を見つけている項目だけで構成する
4. **目標曲線とシミュレーション結果は必ず対で残す**。数値だけ変えて記録が無い変更は、次のサイクルで理由が分からなくなる

## このリポジトリでの実行手段

- シミュレーション：`npx tsx scripts/sim/<game>-<場面>.ts [runs]`（例: `tata-battle.ts`、`tata-stroll.ts`）。ロジックは `src/games/<game>/` の純粋関数を直接 import する
- 検証ゲート：`npm run build`。テストランナーは無いので、シミュレーションが数値の回帰テストを兼ねる
- スクリーンショット：Playwright で `#/<game>` を開き、判断の前の画面を撮る
